Reliability Field Guide

Observability Day One

Understand your telemetry stack by following one request: OpenTelemetry, Application Insights, Azure Managed Grafana, PagerDuty, and Pendo, with the vocabulary, a map of your setup, and a 2-week learning plan.

The Best Way to Learn This

Don't learn the tools one at a time. Follow one user request through your system and name what each tool sees at each step. Once the path is clear, every term (span, collector, sampling) has a place to attach to. This page draws that path for your stack: OpenTelemetry → Azure Monitor / Application Insights → Azure Managed Grafana → PagerDuty, with Pendo for product analytics. Anything marked "confirm" varies by team.

The Big Picture in One Diagram

The diagram in words
  1. Device and client apps send a request to the backend on Azure.
  2. The OpenTelemetry SDK in the backend records traces, metrics, and logs.
  3. Optionally, an OpenTelemetry Collector gathers and forwards them (confirm whether you have one).
  4. They're stored in Application Insights and Log Analytics.
  5. Azure Managed Grafana reads them for dashboards.
  6. Alerts (Grafana Alerting or Azure Monitor) fire on SLOs and thresholds.
  7. PagerDuty routes and escalates the alert.
  8. SRE on-call and the NOC respond.
  9. Separately, the Pendo snippet or SDK in the client apps sends user behaviour (clicks, feature use, feedback) to Pendo.

Follow One Request

14:05. A user asks the assistant to "summarize my unread email." Here's what each tool sees at each hop.

HopWhat happensWhat the telemetry sees
1. Client appUser taps "ask"Pendo records the click, the feature used, and the device type. If the app is instrumented with OTel, it starts a trace and sends the trace ID with the request (confirm).
2. Front door / APIRequest arrives on AzureA span starts: "POST /assistant/ask." The trace ID follows the request from here on.
3. Assistant serviceBuilds the prompt; calls the email toolChild spans: "build prompt" and "tool: email.fetch" (with its duration and success). Logs carry the same trace ID.
4. Model callPrompt sent to the model provider; answer streams backA span for the model call, with the model name and token counts as attributes. The first streamed piece gives TTFT; the end of the span gives TTLT. See AI Latency.
5. ResponseThe answer appears on the deviceThe trace completes. Application Insights shows it in the end-to-end transaction view.
AggregateThousands of these per minuteGrafana panels show p95 TTFT, error rate, and traffic. If the SLO burns too fast, an alert fires and PagerDuty pages on-call.
AfterwardsUser gives a thumbs-downPendo (or an app event) records the feedback, a quality signal.

The Vocabulary You Actually Need

TermPlain meaningYou'll hear it as…
OpenTelemetry (OTel)An open standard and toolkit for producing telemetry, so you aren't locked into one vendor"We instrument with OTel."
Instrumentation (auto vs manual)Code that records telemetry. Auto covers common things (HTTP, databases); manual adds business detail"Is that auto-instrumented?"
TraceThe full journey of one request across services"Pull the trace for that request."
SpanOne step in a trace, with a start, an end, and details"The model-call span took 9 seconds."
Trace ID / context propagationThe ID passed along with a request so every service's spans join up"Context isn't propagating from the app."
Attributes, service.nameLabels on telemetry. service.name says which service sent it"Filter by service.name."
Semantic conventionsAgreed standard names for attributes, so everyone labels things the same way"Use the GenAI semconv names."
CollectorA service that receives, processes, and forwards telemetry"The collector drops debug logs."
ExporterThe piece that sends telemetry to a backend, such as Azure Monitor"We use the Azure Monitor exporter."
SamplingKeeping only a percentage of traces to control cost"We sample at 10%, so we might not have that one."
Counter / histogramMetric types: a running count, and a distribution (used for percentiles like p95)"TTFT is a histogram."
Log correlationLogs stamped with the trace ID, so you can jump from a trace to its logs"Are logs correlated?"
Pendo event / tagged featureA recorded user action, and a UI element tagged so its usage is counted"Is that button tagged in Pendo?"
Pendo guide / segmentAn in-app message or walkthrough, and a defined group of users"Show the guide to the beta segment."

Which Tool Answers Which Question

QuestionGo to
Is it up, slow, or erroring right now?Grafana panels (data from Application Insights)
Why did this one request fail or take so long?Application Insights end-to-end transaction (the trace)
What exactly did the service log?Log Analytics (KQL), filtered by trace ID
What changed?Grafana annotations, the Azure Activity Log, deploy history
Are users still using the feature, or giving up?Pendo (feature usage, funnels, retention)
Who got paged, and when?PagerDuty incident timeline

Ops Telemetry vs Product Analytics

OpenTelemetry → Azure MonitorPendo
PurposeIs the system healthy and fast?What do users do, and do they succeed?
SpeedNear real time, for alertingUsually slower, for analysis and trends
DetailEvery request (or a sample) through every serviceUser actions in the app UI
PrivacyShould avoid personal data in attributes and logsUser-level by design, so handle personal data carefully and follow your privacy rules
Owner (typically)Engineering and SREProduct

In an incident, use both: OTel tells you the system broke and when. Pendo shows how much it changed user behaviour (feature usage dropping, people retrying), and how fast they came back. That's the impact story leadership wants.

Map Your Own Setup: 12 Questions for an Engineer

  1. Which services are instrumented with OpenTelemetry, and which aren't yet?
  2. Is it auto-instrumentation, manual, or both? What business detail do we add manually?
  3. Do we run an OpenTelemetry Collector, or do services export straight to Azure Monitor?
  4. What's our sampling rate, and do we keep 100% of errors?
  5. Is service.name consistent across services and environments?
  6. Do the device apps propagate the trace ID to the backend, or does only Pendo see the client side?
  7. Do model calls record TTFT, TTLT, model name, and token counts?
  8. Are logs correlated with trace IDs?
  9. How long do we keep traces and logs, and what does telemetry cost per month?
  10. Which Grafana dashboards are the official ones for each critical service?
  11. Which alerts route to PagerDuty, and which go to chat or email?
  12. Who owns Pendo, and can SRE see the assistant's usage and feedback data?

A 2-Week Learning Plan (15 Minutes a Day)

DayDo this
1With an engineer, draw the diagram above for your real system. Correct the boxes that differ.
2Ask the 12 questions above (spread over two sessions if needed).
3Open one real request's end-to-end transaction in Application Insights. Name each span.
4Find the model-call span. What were TTFT, TTLT, and the token counts?
5Find the same time window in Grafana. Which panel shows it?
6Look at one alert rule in Grafana or Azure Monitor. Trace where it routes in PagerDuty.
7Open Pendo for the assistant: one funnel, and the feedback for the last week.
8Pick a past incident. Find it in Grafana, PagerDuty, and Pendo.
9Ask: "What couldn't we see during that incident?" Write down the gap.
10Teach it back: explain the whole flow to your boss or a peer in 5 minutes, without notes.

What Good Looks Like

What Done Looks Like

  • Every critical service is instrumented with OpenTelemetry, with a consistent service.name.
  • Traces run end to end, from the client app (or front door) to the model provider call.
  • Model calls record TTFT, TTLT, model, and token counts.
  • Logs carry trace IDs.
  • Each critical service has one official Grafana dashboard, and everyone knows which it is.
  • Sampling, retention, and monthly telemetry cost are written down.
  • Pendo usage and feedback are part of incident impact reporting.
