AI Latency: TTFT, TTLT & Streaming

Time to first token, time to last token, and streaming speed: what each means, what drives it, how to measure it on your stack, and what to do when the assistant is slow.

Use This When

Someone says "the assistant feels slow," you're setting latency targets, or you're reviewing the Performance Engineering scorecard. For streaming AI answers, "latency" is not one number. It's at least three, and they have different causes and fixes.

The Latency Measures, Defined

MeasurePlain meaningWhat users feel
TTFT: time to first tokenFrom sending the request until the first piece of the answer arrives"Is it working?" The most important number for perceived speed.
Time per output token (inter-token latency)The gap between pieces of the answer as it streams"It's typing slowly."
TTLT: time to last token (end-to-end)From sending the request until the full answer is done"How long until I can use the answer?"
Tokens per secondStreaming speed, the inverse of time per output tokenSame as above, often quoted by providers
Queue or wait timeTime waiting before any work starts (rate limits, busy capacity)Adds directly to TTFT

Roughly, TTLT ≈ TTFT + (number of output tokens × time per output token). So a long answer can have a great TTFT and still a slow TTLT.

What Drives Each One

DriverAffectsQuestion to ask
Prompt and context length (instructions, history, retrieved documents)TTFT"How many input tokens per request, and is it growing?"
Retrieval and tool calls before generationTTFT"How much of TTFT is retrieval and tools vs the model?"
Model choice (larger is usually slower)TTFT and streaming speed"Did the model or model version change?"
Provider load, throttling, regionTTFT, errors"Are we being throttled? Which region are we calling?"
Output lengthTTLT"Are answers getting longer? Is there a max token limit?"
Cold starts and scaling on our sideTTFT, mostly at the slowest percentiles"Is it worse after quiet periods or deploys?"

Example SLOs

These are starting points. Confirm the numbers with product, based on what users accept, and on your own last 4 weeks of data.

  • TTFT: 95% of responses start streaming within 1.5 seconds.
  • TTLT: 95% of responses complete within 12 seconds.
  • Success: 99.5% of requests return a usable answer (not an error, a timeout, or an empty answer).

Measure them per user journey: a quick question and a multi-step agent task deserve different targets. See SLOs.

How to Measure It on Your Stack

See where each timing point lives, hop by hop: the Request Map.

  1. Pod engineers: wrap each model call in an OpenTelemetry span with the model name and token counts as attributes. Record the moment the first streamed chunk arrives as a span event or a metric, which gives you TTFT. The span's total duration gives you TTLT.
  2. Standards note: OpenTelemetry's GenAI semantic conventions define names such as gen_ai.request.model, and server-side metrics such as gen_ai.server.time_to_first_token. They're still marked Development and changing, and the server metrics are for teams that run their own models. If you call a third-party provider, measure TTFT in your own client code. Use whatever names your SDK emits, consistently.
  3. Storage: the data lands in Application Insights via the Azure Monitor OpenTelemetry exporter.
  4. Dashboard: Grafana panels for p50, p95, and p99 TTFT and TTLT, split by model, region, and app version, with deploy and prompt-change annotations.
  5. Alerting: burn-rate alerts on the TTFT SLO route to PagerDuty. See Alerting.

When the Assistant Is Slow

A five-question triage you can run on the bridge without touching a keyboard:

  1. Slow to start, or slow to finish? TTFT up points to the prompt, retrieval, queueing, or provider. Only TTLT up points to longer answers or slower streaming.
  2. Everyone, or a segment? Split by region, app version, model, and journey in App Insights or Grafana.
  3. Is the provider throttling or slow? Check the 429 rate and the duration of dependency calls to the provider.
  4. Did the prompt or model change? Look for an annotation or deploy in the last 24 hours. Has input token count jumped?
  5. Is retrieval or a tool call slow? Open one slow request's end-to-end trace in Application Insights and see where the time went.

If the answer points somewhere your team can't change, switch to the Stuck Incident playbook.

Example in Practice

Support reports "the assistant is slow since this morning." p95 TTLT is up 40%, but TTFT is flat. In other words, answers start on time but take longer to finish. Output tokens per answer are up 60% since a prompt change at 08:10 that asked for "more detailed answers." The fix is a product decision about answer length, not an infrastructure problem. Without separating TTFT from TTLT, the team would have spent the morning blaming the provider.

What Actually Happens

Only average latency is tracked.
Counter: averages hide the slowest users. Always ask for p95 and p99.
Latency is measured at the server, not as the user feels it.
Counter: ask whether the device apps report TTFT too (or Pendo-side timing). Network and on-device time can be large.
"The provider is slow."
Counter: ask for one trace broken down by hop before accepting that.
