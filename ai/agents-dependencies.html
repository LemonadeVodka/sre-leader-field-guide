Agents, Tools & Model Providers

Reliability for agent-style assistants: tool calls, multi-step tasks, model provider dependence, fallbacks, degraded modes, and cloud vs on-device paths.

Use This When

The assistant takes actions or calls tools (an agent), depends on a third-party model provider, or runs some work on the device and some in the cloud. Each of these adds ways to fail that a simple "is the API up?" check won't catch.

Agents and Tools

An agent is an assistant that plans and takes steps, such as searching, reading a calendar, or changing a device setting, by calling tools. One user request can turn into 5–10 calls, and any one of them can fail or be slow.

MeasureWhat it tells you
Tool-call success rate, per toolWhich tools are failing, and the owner of each
Task completion rateOf multi-step requests, how many finished successfully
Steps per taskRising steps means more cost, more latency, and possible loops
Time per step, and timeoutsWhere the time goes in a slow agent task
  • Every step needs a timeout, and retries with exponential backoff and a cap, to avoid retry storms.
  • Cap the number of steps per task, so a confused agent can't loop forever and burn tokens.
  • Trace the whole task as one OpenTelemetry trace, with a span per step and per tool call, so one slow task can be opened end to end in Application Insights.

Model Provider Dependence

For most AI assistants, the model provider is the biggest single point of failure. Plan for it the way you'd plan for any critical vendor.

  • Measure it yourself. Track the success rate and latency of your calls to the provider in Application Insights. Status pages lag behind real problems.
  • Fallback routing. A backup model, deployment, or region to route to when the primary is failing or throttling. Make it a pre-approved lever.
  • Degraded modes. Decide in advance what a "good enough" answer looks like when things are failing: answer without tools, give a shorter answer, or show a clear "try again" message instead of a spinner.
  • Contacts and contracts. Know the support path, the SLA, and the quota process for each provider. This is vendor management, which is your home turf.

Cloud vs On-Device

Cross-device assistants may run some requests on the device and some in the cloud. Confirm with your team which requests run where, because it changes what you can see:

  • Cloud requests show up in your backend telemetry (OTel → Application Insights).
  • On-device work may only appear in client telemetry or Pendo, if anywhere. An on-device failure can look like "the backend is fine" while users struggle.
  • Ask: "If the on-device path broke, how would we know?"

What Done Looks Like

  • Success rate and latency are tracked per tool, with an owner for each tool.
  • Task completion rate and steps per task are on the AI dashboard.
  • Every agent step has a timeout, capped retries with backoff, and a step limit.
  • A tested fallback model or route, usable as a pre-approved lever.
  • Written degraded modes, agreed with product.
  • You know which requests run on the device, and how failures there would be detected.

What Actually Happens

One flaky tool makes the whole assistant look broken.
Counter: let the agent continue without a failing tool where possible, and show the per-tool success rate.
The fallback model has never been tested.
Counter: switch to it in a drill once a quarter. An untested fallback is a guess.
"The provider is down" ends the conversation.
Counter: ask "what's our degraded mode, and who decides to switch to it?"
