An AI Assistant on Azure: Request Map

Where each part of a typical AI assistant lives on Azure, where time to first word is measured, what breaks at each hop, and the questions to ask. Written for leaders, not engineers.

A Typical Design, Not Any Specific Product's

This is how a hybrid (on-device plus cloud) AI assistant is commonly built on Azure. Real systems differ. Treat every box as a question, and verify every box with your architects. You don't need to understand how any part works inside. You need to know what it does, what breaks there, and what to ask.

Client App and On-Device Model T0T4T5

Think of it as: The shop counter. It's where the customer asks, and where they see the answer appear.

What it is: The assistant app on the laptop or phone. It sends the message, shows the answer as it streams in, and for some features runs a small AI model right on the device, with no cloud needed.

Where it sits: Start and end of every request. T0 is when the user presses Send; T4 is when the first word appears; T5 is when the last word appears. TTFT users actually feel is T4 minus T0, and only the app can measure it.

Common Issues

  • Feels slow, but the server says it's fast: the delay is on the device or the network, and nobody measures T4.
  • Crashes or freezes after an update to the app or to the on-device model.
  • Different answers on PC and phone because they run different app or model versions.
  • On-device model too heavy for older hardware: battery drain, fans, slow first answer.
  • Works on office Wi-Fi, fails on hotel or VPN networks.

Signals to Check

Time to first token measured in the app (client OpenTelemetry into App Insights) · crash rate by app version · share of users on each version · Pendo feature usage and drop-off. (Typical names; they vary. Confirm with your engineer.)

Questions to Ask

  1. "Do we measure time to first word on the device, or only on the server?"

    If they say "Only on the server" → ask "Can we add one timer in the app? That's the number users actually feel."

    Builds credibility: You know the difference between what servers see and what users feel, which is the core of SRE.

  2. "What app and model versions are users on right now?"

    If they say "We don't know" → ask "Can we get a version breakdown before the next release goes out?"

    Builds credibility: Version spread explains a lot of 'only some users' problems.

  3. "Which features run on the device, and which go to the cloud?"

    If they say "It depends" → ask "Can we write that down per feature? It changes where we look when it breaks."

    Builds credibility: You're mapping failure domains, which is exactly what reliability leaders do.

  4. "What happens when the device is offline?"

    If they say "It just fails" → ask "What should the user see instead, and who decides that?"

    Builds credibility: You think about the user's experience when things fail, not just when they work.

  5. "What's the oldest hardware we support, and how does the assistant perform on it?"

    If they say "We haven't tested" → ask "Can we add one low-end device to release testing?"

    Builds credibility: Asking about the worst case, not the demo machine, signals real-world thinking.

Say this in the room: "Before we look at servers, do we know what the user's device measured for time to first word?"

You don't need to know: How the app is coded or how the on-device model is packaged.

Usually owned by: The client app pod, plus whoever owns on-device models.

CDN and Edge (Azure Front Door + WAF)

Think of it as: A local warehouse next to customers, so they don't wait for shipping from head office. Plus a bouncer (the WAF) at the door.

What it is: The first stop on the internet. It serves files from nearby locations (app updates, on-device model downloads, images), passes chat requests through to the gateway, and blocks bad traffic with a web application firewall (WAF).

Where it sits: Between T0 and T1, on every request. Also the delivery path for app and model downloads.

Common Issues

  • Stale or wrong content after a release, because the cache wasn't cleared.
  • Long streaming answers cut off mid-sentence because a timeout is shorter than the answer.
  • One region slow or down, and traffic doesn't move to a healthy region.
  • Real users blocked after a WAF rule change (false positives).
  • Expired certificate or DNS record: everything fails at once.
  • Large on-device model downloads slow or failing (cache misses, huge files).

Signals to Check

Front Door Total Latency vs Origin Latency (slow at the edge, or slow behind it?) · percentage of 4xx/5xx errors · cache hit ratio · WAF blocked requests · all split by region. (Typical names; they vary. Confirm with your engineer.)

Questions to Ask

  1. "Is this slow at the CDN, or slow behind it?"

    If they say "Not sure" → ask "Can we compare total latency with origin latency for the last hour?"

    Builds credibility: One question splits the problem in half, and you didn't need to touch a config.

  2. "Did we change caching, WAF rules, or routing in the last 24 hours?"

    If they say "No" → ask "Can we check the change history to be sure, not from memory?"

    Builds credibility: You go to change history first, which is where most incidents start.

  3. "What's the timeout for a streaming answer, and is it longer than our longest answer?"

    If they say "I'd have to check" → ask "Can we check it against our slowest real answers this week?"

    Builds credibility: You've connected an edge setting to a real user symptom: answers that stop mid-sentence.

  4. "If one region fails, does traffic move automatically, and when did we last test it?"

    If they say "It should" → ask "Should isn't tested. When can we do a failover drill?"

    Builds credibility: Untested failover is a known trap. Naming it shows experience.

  5. "When do our certificates and DNS records expire, and who gets warned?"

    If they say "They auto-renew" → ask "Who gets told if auto-renew fails?"

    Builds credibility: Certificate expiry outages are embarrassing and preventable. Leaders who ask avoid them.

Say this in the room: "Before we blame the model, can we check whether the delay is at the edge or behind it?"

You don't need to know: How caching rules or WAF rules are written. That's your engineers' job.

Usually owned by: Platform or networking team; security often owns the WAF rules.

Sign-In (Microsoft Entra ID)

Think of it as: The ID check at the building entrance.

What it is: Confirms who the user is and gives the app a pass (a token) to present to everything behind it.

Where it sits: Before T1. Every request carries a token from here.

Common Issues

  • Users suddenly signed out or seeing 'not authorized' (401) after a configuration change.
  • Tokens expiring mid-conversation, so long sessions break.
  • Sign-in outage at the provider: nobody can start a chat.
  • Partner connections (calendar, email) need users to re-approve access.

Signals to Check

Sign-in failure rate and reasons in Entra sign-in logs · 401 count at the gateway · Microsoft service health. (Typical names; they vary. Confirm with your engineer.)

Questions to Ask

  1. "Are these 401s 'who are you?' or 403s 'you're not allowed'?"

    If they say "Both" → ask "Which one is growing? They have different causes."

    Builds credibility: Knowing 401 from 403 is a small detail that signals you understand the plumbing.

  2. "Did anything change in sign-in or app registration settings recently?"

    If they say "No" → ask "Can we check the audit log for the last 48 hours?"

    Builds credibility: You go to evidence instead of accepting 'no'.

  3. "What happens to a user's chat when their sign-in expires mid-conversation?"

    If they say "It errors" → ask "Can we refresh silently instead? Who decides?"

    Builds credibility: You think in user journeys, not components.

  4. "If sign-in is down, what does the user see?"

    If they say "A generic error" → ask "Can we show a clear message and a status link?"

    Builds credibility: Graceful failure is a reliability habit leaders notice.

  5. "Who owns sign-in configuration for the assistant?"

    If they say "Identity team, I think" → ask "Can we confirm a name for the escalation list?"

    Builds credibility: You close ownership gaps before an incident does.

Say this in the room: "Is this a who-are-you problem or a you're-not-allowed problem?"

You don't need to know: How tokens are signed or how scopes are configured.

Usually owned by: Identity or security team.

API Gateway (Azure API Management) T1

Think of it as: The security desk and receptionist. Checks your pass, counts visitors, and says 'too many, wait' when it's busy.

What it is: The single front desk for the assistant's services. It checks tokens, applies per-user and per-app limits, routes requests to the right service, and records how long everything behind it took.

Where it sits: T1: the request has arrived in our cloud. Everything after this is 'behind the gateway'.

Common Issues

  • 429 'too many requests' from our own per-user or per-app limits, the first of three places a 429 can come from.
  • Gateway itself overloaded at peak, adding delay to every request.
  • A routing or policy change sends traffic to the wrong place.
  • Timeouts set shorter than the slowest answer, cutting off long responses.

Signals to Check

Requests by response code (watch 429, 5xx) · overall duration vs backend duration (is the delay the gateway or behind it?) · gateway capacity. (Typical names; they vary. Confirm with your engineer.)

Questions to Ask

  1. "Are these 429s coming from our gateway limits, or from further back?"

    If they say "Not sure" → ask "Can we split 429s by source: gateway, model, and database?"

    Builds credibility: There are three places a 429 can come from. Knowing that cuts troubleshooting time in half.

  2. "How much of the delay is the gateway, and how much is behind it?"

    If they say "It's all slow" → ask "Can we compare overall duration with backend duration?"

    Builds credibility: You're isolating the slow hop without needing to read any code.

  3. "What are our per-user limits, and who set them?"

    If they say "Default settings" → ask "Do they still fit how people use the assistant today?"

    Builds credibility: Defaults are often wrong at scale. Asking about them shows judgment.

  4. "Did any gateway policy change this week?"

    If they say "Maybe" → ask "Can we see the change history and who approved it?"

    Builds credibility: Change history first, every time. That habit builds trust.

  5. "What's the gateway's capacity at peak, and how close are we?"

    If they say "We've never hit it" → ask "When's the next launch, and will we?"

    Builds credibility: You're thinking ahead to load, not waiting to be surprised.

Say this in the room: "Is the time going at the front desk or behind it?"

You don't need to know: How gateway policies are written.

Usually owned by: Platform or API team.

Orchestrator (Container Apps, AKS, or App Service) T2

Think of it as: The project manager. Takes the request, gathers what's needed (history, documents, tools), briefs the writer (the model), and passes the answer back.

What it is: Our main code. It builds the prompt, decides which tools or data to use, calls the safety checks and the model, and streams the answer back.

Where it sits: Between T1 and T2 it prepares; at T2 it calls the model. Most 'prep time' in TTFT lives here.

Common Issues

  • Slow prep before the model is even called: too many lookups, slow memory or search.
  • Cold starts: the first request after a quiet period is very slow because servers are starting up.
  • Not enough copies (replicas) running at peak.
  • A code or prompt change makes answers worse or slower.
  • One slow tool or partner holds the whole answer hostage.

Signals to Check

Request duration and failure rate · time spent before the model call (T2 minus T1) · replica count and restarts · CPU and memory · dependency calls in App Insights. (Typical names; they vary. Confirm with your engineer.)

Questions to Ask

  1. "How long do we spend before we even call the model?"

    If they say "Not sure" → ask "Can we time T1 to T2 separately? That's our part of TTFT."

    Builds credibility: You've split TTFT into what we control and what the model controls.

  2. "Do we get slow first requests after quiet periods?"

    If they say "Sometimes" → ask "Do we keep a minimum number of servers warm?"

    Builds credibility: Cold starts are a classic hidden latency. Naming them sounds experienced.

  3. "What changed in our code or prompts in the last 24 hours?"

    If they say "Nothing major" → ask "Can we check deploys and prompt versions, not memory?"

    Builds credibility: You treat prompts as changes, which many teams forget.

  4. "If one tool is slow, does the whole answer wait?"

    If they say "Yes" → ask "Can we set a time limit per tool and answer without it?"

    Builds credibility: You're designing for partial failure, which is mature reliability thinking.

  5. "How many copies run at peak, and does it scale up automatically?"

    If they say "It should" → ask "When did we last see it scale under real load?"

    Builds credibility: You ask for evidence of scaling, not assumptions.

Say this in the room: "How much of the time to first word is our prep work, before the model starts?"

You don't need to know: The orchestration code or framework.

Usually owned by: The assistant pod.

Settings and Feature Flags (Azure App Configuration)

Think of it as: The light switches. Turn features, prompt versions, and model choices on or off without a new release.

What it is: Central settings: which prompt version, which model, which features are on for which users.

Where it sits: Read by the orchestrator on every request. Not a hop users wait on, but a common source of silent changes.

Common Issues

  • A prompt or model switch flipped quietly, and answers change overnight.
  • A feature turned on for everyone instead of 5% of users.
  • Settings differ between regions, so only some users see the problem.
  • Nobody knows who changed what, or when.

Signals to Check

Setting and flag change history (who, what, when) · which version each region is using. (Typical names; they vary. Confirm with your engineer.)

Questions to Ask

  1. "Did any setting, flag, or prompt version change in the last 24 hours?"

    If they say "No deploys" → ask "Settings change without deploys. Can we check the flag history?"

    Builds credibility: You know changes hide outside deployments, which most people miss.

  2. "Are settings the same in every region?"

    If they say "They should be" → ask "Can we compare them? 'Only some users' often lives here."

    Builds credibility: You connect a vague symptom to a concrete check.

  3. "Who can change prompts and model settings in production?"

    If they say "A few people" → ask "Is every change reviewed and logged?"

    Builds credibility: Asking about change control without owning it is exactly your level.

  4. "Do we roll features out gradually?"

    If they say "Sometimes" → ask "Can we make gradual the default for anything user-facing?"

    Builds credibility: Staged rollouts are basic safe-change practice.

  5. "How fast can we switch a bad setting back?"

    If they say "Pretty fast" → ask "Who can do it at 2 a.m., and is it in the runbook?"

    Builds credibility: You turn 'pretty fast' into a named person and a written step.

Say this in the room: "No deploy doesn't mean no change. Did any flag or prompt version move?"

You don't need to know: How flags are stored or evaluated.

Usually owned by: The assistant pod; platform owns the service itself.

Safety Filters (Azure AI Content Safety)

Think of it as: The editor who checks what goes in and what comes out, and can stop the presses.

What it is: Checks the user's message before the model sees it, and the model's answer as it's produced, for harmful content or attempts to trick the model.

Where it sits: Just before T2 and while the answer streams back. Adds a little time to every request.

Common Issues

  • Harmless questions blocked (false positives) after a filter setting changes.
  • Answers cut off mid-stream because the output check triggered.
  • Extra delay on every request from the checks.
  • Users see a confusing error instead of a clear 'I can't help with that.'

Signals to Check

Count of filtered requests and responses, by category · added time per check · user reports of 'it refused a normal question.' (Typical names; they vary. Confirm with your engineer.)

Questions to Ask

  1. "How many requests did the safety filters block this week, and is that changing?"

    If they say "Not sure" → ask "Can we track it weekly? A jump usually means a setting changed."

    Builds credibility: You treat safety as something to measure, not a black box.

  2. "When the filter blocks something, what does the user see?"

    If they say "An error" → ask "Can we show a clear, friendly message instead?"

    Builds credibility: You care about the experience even when the answer is no.

  3. "Did the cut-off answers coincide with filter triggers?"

    If they say "Maybe" → ask "Can we check the filter logs for those conversations?"

    Builds credibility: You've connected a symptom to a less obvious cause.

  4. "How much time do the checks add to each request?"

    If they say "A little" → ask "How much is a little, in milliseconds, at p95?"

    Builds credibility: You turn vague answers into numbers.

  5. "Who decides the filter settings?"

    If they say "Responsible AI team" → ask "Are they on our escalation list for incidents?"

    Builds credibility: You make sure decision-makers are reachable before you need them.

Say this in the room: "Was this answer cut off by the model, the edge, or the safety filter?"

You don't need to know: How the classifiers work.

Usually owned by: Responsible AI or trust team, with the assistant pod.

Conversation Memory (Azure Cosmos DB)

Think of it as: A giant, global filing cabinet with copies in several cities. You're billed by how hard you open the drawers (request units).

What it is: Stores conversations, user preferences, and other data the assistant remembers, replicated across regions so your phone and PC see the same history.

Where it sits: Read during prep (T1 to T2) to load history; written after the answer. Slow reads add directly to TTFT.

Common Issues

  • 429 'too many requests' because we used up our request units (RU), the third place a 429 can come from.
  • A 'hot partition': one very heavy user or key overloads one drawer while others sit idle.
  • History written on the PC doesn't show on the phone yet (replication lag between regions).
  • Data deleted early by an expiry rule (TTL), so 'it forgot our conversation.'
  • Costs spike because a change made every request read more data.

Signals to Check

Requests by status code (429) · normalized RU consumption (near 100% means throttling) · server-side latency · replication latency between regions · availability. (Typical names; they vary. Confirm with your engineer.)

Questions to Ask

  1. "Which 429 is it: gateway, model, or Cosmos?"

    If they say "Just 429s" → ask "Can we split them by source? Cosmos 429s mean we're out of request units."

    Builds credibility: Most people don't know there are three. You do.

  2. "Is one partition hot, or is load spread evenly?"

    If they say "What's a partition?" → ask "Is one user or key getting far more traffic than the rest?"

    Builds credibility: Hot partitions are a classic Cosmos problem. Asking about them earns engineers' respect.

  3. "How long until a message written on the PC shows up on the phone?"

    If they say "It's instant" → ask "Can we measure it? Replication between regions takes time."

    Builds credibility: You've connected a user complaint to a specific technical cause.

  4. "Do we delete old conversations automatically, and does the user know when?"

    If they say "There's a TTL" → ask "Is it what the product promised users?"

    Builds credibility: You're linking a database setting to a user promise and to privacy.

  5. "When did we last test restoring data from backup?"

    If they say "Never" → ask "Can we do one restore test this quarter?"

    Builds credibility: Untested backups aren't backups. Leaders who ask that are taken seriously.

Say this in the room: "Are we out of request units, or is one partition hot?"

You don't need to know: How partition keys are designed or how queries are written.

Usually owned by: The assistant pod, with platform or data team support.

Retrieval and Search (Azure AI Search)

Think of it as: The research assistant who pulls the right files before the writer starts.

What it is: Finds relevant documents, notes, or memories to give the model as context (often called RAG: retrieval-augmented generation).

Where it sits: During prep (T1 to T2). Slow search makes a slow first word; bad search makes wrong answers.

Common Issues

  • Wrong or outdated answers because the index hasn't been refreshed.
  • Slow searches add seconds before the model is even called.
  • Throttling at peak.
  • Private documents showing up for the wrong user (a permissions bug, and a serious one).

Signals to Check

Search latency at p95 · throttled queries percentage · when the index was last updated · number of documents. (Typical names; they vary. Confirm with your engineer.)

Questions to Ask

  1. "When was the search index last refreshed?"

    If they say "It's automatic" → ask "Can we see the last successful refresh time?"

    Builds credibility: Stale data is a quiet cause of wrong answers. Asking shows you know it.

  2. "How long does search take at p95?"

    If they say "Fast" → ask "How many milliseconds, and how much of our prep time is it?"

    Builds credibility: You keep pulling vague answers into numbers.

  3. "Could a user ever see someone else's documents?"

    If they say "No" → ask "How do we know? When was it tested?"

    Builds credibility: You're asking the privacy question nobody wants to be asked later.

  4. "If search is slow or down, does the assistant still answer?"

    If they say "It fails" → ask "Could it answer without the documents and say so?"

    Builds credibility: Graceful degradation is mature reliability design.

  5. "Do wrong answers trace back to bad search results or to the model?"

    If they say "Hard to tell" → ask "Can we log what search returned for a few bad answers?"

    Builds credibility: You're separating retrieval problems from model problems, which is key for AI quality.

Say this in the room: "Is this a bad answer from the model, or did search hand it the wrong documents?"

You don't need to know: How indexes or embeddings are built.

Usually owned by: The assistant pod or a data and search team.

The Model (Azure OpenAI / AI Foundry, or a Provider) T3

Think of it as: A very fast writer you rent by the word, with a limit on how many words per minute you can buy.

What it is: The large language model that writes the answer. You rent capacity measured in tokens (word pieces) per minute, per region.

Where it sits: T2 to T3 is model TTFT: from asking the model to its first word. Usually the biggest single piece of TTFT.

Common Issues

  • 429s because we hit our tokens-per-minute or requests-per-minute limit, the second place a 429 can come from.
  • Slow first word at peak because the provider is busy in that region.
  • Answers change after the provider updates the model version.
  • One region's capacity runs out while others are fine.
  • Context too long: the conversation plus documents don't fit, causing errors or forgotten history.

Signals to Check

Requests by status code (429) · time to first token from the model, often called time to response · tokens per minute used vs limit · latency by deployment and region · model version in use. (Typical names; they vary. Confirm with your engineer.)

Questions to Ask

  1. "What's the model's own time to first token right now, compared with last week?"

    If they say "Not sure" → ask "Can we separate model TTFT from our prep time?"

    Builds credibility: You've isolated the part we don't control from the part we do.

  2. "How close are we to our tokens-per-minute limit at peak?"

    If they say "We're fine" → ask "What's the peak percentage, and what happens at 100%?"

    Builds credibility: Quota is the most common AI outage cause. Asking early is credible.

  3. "Did the model version change recently?"

    If they say "No" → ask "Can we confirm which version each deployment is on today?"

    Builds credibility: Silent model updates change behavior. Few managers know to ask.

  4. "If this region runs out of capacity, where does traffic go?"

    If they say "Nowhere" → ask "Can we add a second region or fallback model? Who decides?"

    Builds credibility: You're asking about a single point of failure in plain words.

  5. "What's our longest conversation, and does it fit the context window?"

    If they say "Probably" → ask "What happens when it doesn't: error, or silently forgetting?"

    Builds credibility: You understand context limits without needing the math.

Say this in the room: "Is the delay our prep work, or is the model itself slow to start?"

You don't need to know: Model internals, sampling settings, or prompt engineering details.

Usually owned by: AI platform team; the assistant pod owns how it's used.

Tools and Agents (Azure Functions)

Think of it as: Specialist contractors the project manager can call: one checks the calendar, one changes a device setting, one books something.

What it is: Small services the assistant calls to look things up or take actions. Agents can chain several tools in one request.

Where it sits: Between T1 and T2 (or in the middle of an answer). Each tool adds time and a new way to fail.

Common Issues

  • One slow tool delays the whole answer.
  • An action runs twice (a duplicate booking or message) after a retry.
  • An agent loops, calling tools again and again, burning time and tokens.
  • A tool fails silently and the model answers as if it worked.

Signals to Check

Duration and failure rate per tool · number of tool calls per request · retries · cost per request. (Typical names; they vary. Confirm with your engineer.)

Questions to Ask

  1. "Which tool is slowest, and does the answer wait for it?"

    If they say "Not sure" → ask "Can we list tool durations at p95 for the top five?"

    Builds credibility: You're finding the slowest link without reading code.

  2. "If a tool call is retried, could the action happen twice?"

    If they say "Hopefully not" → ask "How do we prevent duplicates? Has it been tested?"

    Builds credibility: Duplicate actions are a real-world agent failure. Asking shows foresight.

  3. "Is there a limit on how many tool calls one request can make?"

    If they say "No" → ask "Can we add one, so an agent can't loop forever?"

    Builds credibility: You're putting guardrails on agents, which is current best practice.

  4. "When a tool fails, does the user find out?"

    If they say "Not always" → ask "Can the assistant say 'I couldn't do that' instead of pretending?"

    Builds credibility: Honest failure builds user trust, and you thought of it.

  5. "Who owns each tool?"

    If they say "Various teams" → ask "Can we list an owner per tool on the escalation sheet?"

    Builds credibility: Every dependency needs a name. You're making sure it has one.

Say this in the room: "Is one tool holding up the whole answer?"

You don't need to know: How each tool is coded.

Usually owned by: The assistant pod, or the team that owns each tool.

Integration Platform (iPaaS, such as Workato)

Think of it as: A switchboard operator connecting the assistant to other companies' apps, using pre-built 'recipes'.

What it is: A service that runs automations (recipes) and connections to other apps, so the assistant can read or act in them without custom code for each one.

Where it sits: Called by tools during a request, or in the background (for example, gathering items for a catch-up digest).

Common Issues

  • A connection's login expired, so a recipe quietly stops working.
  • The partner app's rate limits hit, slowing or failing recipes.
  • A recipe paused or errored, and nobody was alerted.
  • Retries create duplicates (two messages, two calendar entries).
  • The partner changed a field, and the data mapping breaks.

Signals to Check

Failed jobs per recipe · connection status (connected or expired) · job duration · alerts on recipe errors (if set up). (Typical names; they vary. Confirm with your engineer.)

Questions to Ask

  1. "Who gets alerted when a recipe fails, and how fast?"

    If they say "We check the dashboard" → ask "Can failures page someone or post to a channel automatically?"

    Builds credibility: Silent failure is the biggest integration risk. Asking about alerting shows you know it.

  2. "Which connections expire, and when?"

    If they say "Not sure" → ask "Can we list them with expiry dates and an owner?"

    Builds credibility: Expired connections cause many 'it just stopped working' incidents.

  3. "What does the user see when a partner is down?"

    If they say "An error" → ask "Can we show 'that service is unavailable' and continue?"

    Builds credibility: You think about partners failing, not just working.

  4. "Do we have a status page and a contact for each partner?"

    If they say "Some" → ask "Can we add the missing ones to the escalation sheet?"

    Builds credibility: Knowing who to call before you need to is basic incident readiness.

  5. "Is a response time for problems in our contract with the platform and partners?"

    If they say "I don't know" → ask "Can someone check with vendor management?"

    Builds credibility: You connect reliability to contracts, which is where senior leaders operate.

Say this in the room: "Did a recipe fail, or did a partner connection expire?"

You don't need to know: How recipes are built.

Usually owned by: An integrations team; vendor management for contracts.

Partner and Third-Party APIs

Think of it as: Other companies' front desks. You can't control their opening hours.

What it is: Services run by other companies that the assistant uses: web answers, notes apps, travel booking, calendars, email, image creation, and so on.

Where it sits: During a request (via tools or the integration platform). Their speed becomes your speed.

Common Issues

  • Their outage looks like our outage to users.
  • Their rate limits throttle us at peak.
  • Their slow responses stall our whole answer.
  • Their changes (new versions, new terms) break us without warning.

Signals to Check

Duration and failure rate per partner (App Insights dependency calls) · partner status pages · partner rate-limit responses. (Typical names; they vary. Confirm with your engineer.)

Questions to Ask

  1. "If this partner is slow, does our whole answer wait?"

    If they say "Yes" → ask "Can we time out and answer without them?"

    Builds credibility: You protect users from problems you can't control.

  2. "How do we find out a partner is down: from them, or from our users?"

    If they say "Users" → ask "Can we monitor their responses and subscribe to their status page?"

    Builds credibility: Finding out before users do is a core SRE goal.

  3. "What does our contract say about their uptime and response?"

    If they say "Not sure" → ask "Can vendor management send me the SLA terms?"

    Builds credibility: Leaders who know the contract terms negotiate from strength.

  4. "Are we near any of their rate limits?"

    If they say "Don't know" → ask "Can we see their limit responses over the last month?"

    Builds credibility: You're spotting a capacity limit that sits outside your company.

  5. "Who do we call at the partner during an incident?"

    If they say "Support email" → ask "Is there an urgent contact, and is it on our escalation list?"

    Builds credibility: A support email at 2 a.m. isn't a plan. Asking now is credible.

Say this in the room: "Is this us, or is it the partner? How would we know?"

You don't need to know: Their internal architecture.

Usually owned by: The integrations or partnerships team, plus vendor management.

Background Messaging (Service Bus / Event Hubs)

Think of it as: The internal mail room. Work that doesn't need to happen right now goes in the mail tray.

What it is: Queues and event streams for work done in the background: feedback, logs, catch-up digests, analytics, notifications to other devices.

Where it sits: Mostly after the answer, or ahead of time. Problems show as delays, not as a slow first word.

Common Issues

  • The queue backs up, so digests or notifications arrive late.
  • Messages that keep failing pile up in the 'dead letter' tray and nobody looks.
  • Event streams throttled at peak, so analytics or feedback go missing.
  • Duplicate processing sends the same notification twice.

Signals to Check

Active messages (queue length) over time · dead-lettered messages · incoming vs outgoing rate · throttled requests. (Typical names; they vary. Confirm with your engineer.)

Questions to Ask

  1. "How many messages are waiting, and is it growing?"

    If they say "Some" → ask "Is it going up or down over the last hour?"

    Builds credibility: Queue growth is an early warning. You're reading it like an ops leader.

  2. "Who looks at the dead-letter queue, and how often?"

    If they say "Nobody" → ask "Can we alert when it's not empty?"

    Builds credibility: Dead letters are silent failures. Asking puts a name on them.

  3. "If background work is delayed, what does the user notice?"

    If they say "Not much" → ask "What about catch-up digests or cross-device notifications?"

    Builds credibility: You connect invisible plumbing to visible features.

  4. "Can a message be processed twice?"

    If they say "Possibly" → ask "What's the effect for the user, and is it handled?"

    Builds credibility: Duplicate-safe processing is a reliability fundamental.

  5. "What happens to queued work if a region fails?"

    If they say "Not sure" → ask "Can we find out before we need to?"

    Builds credibility: You think about failure modes ahead of time.

Say this in the room: "Is the queue growing, and is anyone watching the dead letters?"

You don't need to know: How queues or topics are configured.

Usually owned by: Platform team, with each pod owning its own queues.

Keys and Secrets (Azure Key Vault)

Think of it as: The key cabinet. If a key expires, doors stop opening all at once.

What it is: Stores passwords, keys, and certificates our services use to talk to each other, the model, and partners.

Where it sits: Used behind the scenes on almost every hop. Rarely slow, but when a key expires, things fail suddenly.

Common Issues

  • An expired key or certificate causes sudden 401/403 errors on one connection.
  • A secret rotated in one place but not another.
  • Access to the vault itself is denied after a permission change.
  • Nobody gets warned before expiry.

Signals to Check

Expiry dates for keys, secrets, and certificates · access-denied events · alerts before expiry. (Typical names; they vary. Confirm with your engineer.)

Questions to Ask

  1. "What expires in the next 30 days?"

    If they say "Not sure" → ask "Can we get a list with owners and alerts?"

    Builds credibility: Expiry outages are entirely preventable. Asking prevents them.

  2. "Who gets warned before a key or certificate expires?"

    If they say "It's automated" → ask "Who receives the warning, and has it ever fired?"

    Builds credibility: You test that the safety net exists.

  3. "Did these 401/403 errors start at a round time, like midnight?"

    If they say "Maybe" → ask "That often means something expired. Can we check?"

    Builds credibility: A small, sharp question that often finds the cause.

  4. "When we rotate a secret, does everything that uses it get updated?"

    If they say "Should be" → ask "Is there a checklist or is it automated?"

    Builds credibility: You're asking about the step that often gets missed.

  5. "Who can change vault permissions?"

    If they say "A few people" → ask "Are changes logged and reviewed?"

    Builds credibility: Access control questions without owning the work: right level.

Say this in the room: "Did something expire? These errors started at midnight."

You don't need to know: How secrets are encrypted or stored.

Usually owned by: Security or platform team.

Telemetry (OpenTelemetry → App Insights → Grafana → PagerDuty, plus Pendo)

Think of it as: The CCTV and the alarm system. It doesn't run the shop, but without it you're guessing.

What it is: How we see everything above: OpenTelemetry collects timings and errors, App Insights and Log Analytics store them, Azure Managed Grafana shows dashboards, PagerDuty wakes people up. Pendo shows what users do in the app.

Where it sits: Every hop reports here. If T0 to T5 aren't recorded, you can't tell where time goes.

Common Issues

  • Missing timings: the hop that's slow isn't measured.
  • Sampling hides rare but painful failures.
  • Alerts fire on server metrics, not on what users feel.
  • Data gaps during the incident itself (the pipeline is affected too).
  • Pendo and server data don't line up, so product and engineering argue about numbers.

Signals to Check

Which of T0 to T5 are actually recorded · data ingestion volume and gaps · alert count per week and how many were acted on. (Typical names; they vary. Confirm with your engineer.)

Questions to Ask

  1. "Which of T0 to T5 do we actually record today?"

    If they say "Most of them" → ask "Which ones are missing? That's where we're blind."

    Builds credibility: You've turned observability into a concrete checklist.

  2. "Do our alerts fire on what users feel, like time to first word, or on CPU?"

    If they say "CPU mostly" → ask "Can we add one alert on user-facing TTFT?"

    Builds credibility: User-facing alerting is the heart of SRE. You're steering toward it.

  3. "Are we sampling, and could we miss rare failures?"

    If they say "Yes, we sample" → ask "Do errors always get kept, even when we sample?"

    Builds credibility: A precise question that shows you understand trade-offs.

  4. "During the last incident, were there gaps in our data?"

    If they say "A few" → ask "Can we make sure telemetry doesn't share the same failure point?"

    Builds credibility: You're asking whether the alarm works when the building's on fire.

  5. "Do Pendo and our server numbers agree on usage?"

    If they say "Roughly" → ask "Can we reconcile one number together this month?"

    Builds credibility: You're bridging product and engineering, a leadership move.

Say this in the room: "Which of these hops can we actually see right now?"

You don't need to know: How OpenTelemetry is configured or how queries are written.

Usually owned by: SRE (likely your team), with each pod instrumenting its own code.

Features, and How They're Probably Built

Common features of a personal AI assistant, and how each would typically be built on Azure. This is a best guess for any real product. Open one to see what it touches and what to ask.

Chat With History Across Devices

What users see: Ask anything; pick up the same conversation on your PC or phone.

How it's probably built: The app sends the message through the edge and gateway to the orchestrator, which loads recent history from Cosmos DB, calls the model, streams the answer back, and saves the turn. Cosmos DB is replicated across regions so other devices see it.

Touches: App on PC or phone, CDN and edge, API gateway, Orchestrator, Cosmos DB (memory), The model

Where the time goes: Loading history (Cosmos DB) adds to prep time; the model's first word is usually the biggest part.

What breaks:

  • History missing on the other device (replication lag).
  • Slow start when history is long or Cosmos DB is throttled.
  • 'It forgot what I said' when the conversation outgrows the context window.

Questions to ask:

  1. "How long until a message on the PC shows on the phone?"

    If they say "Instantly" → ask "Can we measure it once this week?"

    Builds credibility: You've turned a user complaint into a measurable number.

  2. "What happens when a conversation gets too long for the model?"

    If they say "It trims it" → ask "What gets dropped, and does the user know?"

    Builds credibility: You understand context limits in user terms.

  3. "Are Cosmos DB 429s showing up at peak?"

    If they say "Not sure" → ask "Can we check request-unit usage at peak?"

    Builds credibility: You know the database has its own 429.

Personal Memory and Knowledge Base

What users see: The assistant remembers your preferences and can find things from your own notes and documents, if you allow it.

How it's probably built: Probably an on-device index for private data, plus a cloud store with vector search (Cosmos DB vector search or Azure AI Search), an embeddings model to make text searchable, and consent flags checked on every lookup.

Touches: App on PC or phone, Orchestrator, Cosmos DB (memory), Search (retrieval), The model, Safety filters

Where the time goes: Searching memories adds to prep time before the model starts.

What breaks:

  • Stale or missing memories (index not refreshed).
  • A user withdraws consent but old data is still used.
  • Wrong person's data surfaced (permissions bug).

Questions to ask:

  1. "When a user turns memory off, how fast is their data really gone?"

    If they say "Right away" → ask "Including backups and the search index?"

    Builds credibility: Privacy questions asked early protect the company and your credibility.

  2. "How do we check one user can never see another's memories?"

    If they say "It's designed that way" → ask "When was it last tested?"

    Builds credibility: You ask for evidence on the highest-stakes failure.

  3. "How much time does the memory lookup add to the first word?"

    If they say "A bit" → ask "How many milliseconds at p95?"

    Builds credibility: You keep latency in numbers.

Proactive Suggestions

What users see: One-tap suggestions for what to do next, based on what you're doing.

How it's probably built: Probably on-device signals (what's on screen, the current app) feed a small on-device model, with occasional cloud calls. Acceptance tracked in Pendo and events sent via Event Hubs.

Touches: App on PC or phone, The model, Background messaging, Telemetry

Where the time goes: Mostly on the device: it must be fast and light on battery.

What breaks:

  • Suggestions irrelevant or annoying (quality).
  • Battery or CPU drain on older devices.
  • Cloud fallback slow on poor networks.

Questions to ask:

  1. "What share of suggestions do people actually tap?"

    If they say "Not sure" → ask "Can Pendo show acceptance by suggestion type?"

    Builds credibility: You measure usefulness, not just uptime.

  2. "What does this cost in battery on our oldest supported device?"

    If they say "We haven't measured" → ask "Can we add it to release testing?"

    Builds credibility: Device impact is reliability users feel.

  3. "How much runs on the device versus the cloud?"

    If they say "Mostly device" → ask "What happens when the cloud part is slow?"

    Builds credibility: You map the failure domains.

Writing Help

What users see: Drafts and fixes emails, documents, and messages in your tone.

How it's probably built: Probably an on-device model first for speed and privacy, with a cloud model fallback for longer or harder drafts, plus safety checks.

Touches: App on PC or phone, Orchestrator, Safety filters, The model

Where the time goes: On-device answers are fast; cloud fallback adds the full request path.

What breaks:

  • Quality jumps between on-device and cloud answers.
  • Fallback to cloud slow or failing on bad networks.
  • Safety filter blocks a normal business email.

Questions to ask:

  1. "How often do we fall back from on-device to cloud?"

    If they say "Not sure" → ask "Can we track it? A jump means something changed."

    Builds credibility: You know hybrid designs hide a second failure path.

  2. "Do users notice a quality difference between the two?"

    If they say "Maybe" → ask "Can we compare thumbs-down rates for each?"

    Builds credibility: You measure quality, not just speed.

  3. "What happens offline?"

    If they say "On-device still works" → ask "Has it been tested on our lowest-spec device?"

    Builds credibility: You check the promise against reality.

Live Voice, Screen, and Camera

What users see: Talk to the assistant about what's on your screen or in front of your camera, in real time.

How it's probably built: Probably a real-time multimodal model over a long-lived connection (WebSocket or WebRTC), possibly with Azure AI Speech for voice, passing through the edge.

Touches: App on PC or phone, CDN and edge, API gateway, Orchestrator, The model, Safety filters

Where the time goes: Measured as time to first audio, not just first token. Network quality matters a lot.

What breaks:

  • Connections drop because the edge or gateway times out long sessions.
  • Lag on poor networks.
  • High cost per minute if sessions are left open.

Questions to ask:

  1. "What's our time to first audio, and what's the target?"

    If they say "Not tracked" → ask "Can we measure it like TTFT?"

    Builds credibility: You extend TTFT thinking to voice.

  2. "What's the longest a live session can stay connected before the edge cuts it?"

    If they say "Not sure" → ask "Is that longer than a typical session?"

    Builds credibility: You've linked an edge timeout to a feature.

  3. "Do idle sessions close automatically?"

    If they say "Eventually" → ask "What does an idle hour cost us?"

    Builds credibility: You connect reliability to cost.

Catch-Up Digest

What users see: A summary of what you missed: messages, calendar changes, and document edits.

How it's probably built: Probably background jobs (Azure Functions plus Service Bus) that pull from email, chat, calendar, and documents via connectors (Microsoft Graph, Slack, or an integration platform such as Workato), summarize with the model, and store the digest in Cosmos DB, ready when you open it.

Touches: Background messaging, Tools and agents, Integration platform, Partner services, The model, Cosmos DB (memory)

Where the time goes: Prepared ahead of time; problems show as stale or missing digests, not a slow first word.

What breaks:

  • A connection expired, so one source is silently missing.
  • Partner rate limits slow the background jobs.
  • The digest queue backs up at Monday morning peak.

Questions to ask:

  1. "If one source fails, does the digest say so?"

    If they say "No" → ask "Can it say 'calendar unavailable' instead of leaving it out?"

    Builds credibility: Silent gaps erode trust. You spotted one.

  2. "Who's alerted when a connector or recipe fails?"

    If they say "Nobody, yet" → ask "Can failures post to a channel automatically?"

    Builds credibility: Integration alerting is where most silent failures hide.

  3. "How fresh is the digest when users open it?"

    If they say "Pretty fresh" → ask "Can we measure the age at open?"

    Builds credibility: You define freshness as a number.

Meeting Transcription and Translation

What users see: Live transcription and translation during meetings, then a summary of key points.

How it's probably built: Probably on-device or Azure AI Speech real-time transcription and translation, then the model summarizes in chunks for long meetings, stored for later.

Touches: App on PC or phone, Orchestrator, The model, Cosmos DB (memory), Background messaging

Where the time goes: Real-time lag matters during the meeting; summary time matters after.

What breaks:

  • Transcription lags or drops on poor audio or networks.
  • Long meetings exceed the context window, so summaries miss the end.
  • Consent: not everyone in the meeting agreed.

Questions to ask:

  1. "How far behind real time does transcription run?"

    If they say "A little" → ask "How many seconds at p95?"

    Builds credibility: You keep it measurable.

  2. "How do we summarize a two-hour meeting that doesn't fit the model?"

    If they say "We chunk it" → ask "Is the end of the meeting covered as well as the start?"

    Builds credibility: You understand context limits in a real scenario.

  3. "How do we handle consent from other people in the meeting?"

    If they say "The user decides" → ask "Has legal reviewed that?"

    Builds credibility: You raise risk early, at the right level.

Image Creation

What users see: Create and edit images on the device, with the cloud for advanced work.

How it's probably built: Probably an on-device image model downloaded through the CDN, with a cloud path for heavier jobs, plus safety filters.

Touches: App on PC or phone, CDN and edge, Orchestrator, The model, Safety filters

Where the time goes: First run may wait for a large model download; then speed depends on the device's AI chip.

What breaks:

  • Large model downloads slow or failing (CDN).
  • Unsupported hardware gets a poor experience.
  • Safety filters block harmless images.

Questions to ask:

  1. "How big is the model download, and how long does it take on a typical connection?"

    If they say "It's big" → ask "What does the user see while it downloads?"

    Builds credibility: You think about the first-run experience.

  2. "What's our CDN cache hit rate for model files?"

    If they say "Not sure" → ask "Can we check it after the next release?"

    Builds credibility: You link a feature to the edge.

  3. "Which devices can run it well, and what happens on others?"

    If they say "Newer ones" → ask "Do we tell users, or do they just see it slow?"

    Builds credibility: Setting expectations is part of reliability.

Partner Answers and Bookings

What users see: Answers from a web search partner, search across a notes app, travel options with hand-off to booking.

How it's probably built: Probably tools called by the orchestrator, through an outbound gateway or the integration platform, to partner APIs, with the user's permission (OAuth) and hand-off links to finish in the partner's app.

Touches: Orchestrator, Tools and agents, Integration platform, Partner services, Sign-in

Where the time goes: Partner speed becomes our speed if the answer waits for them.

What breaks:

  • Partner outage looks like ours.
  • The user's permission to a partner expired.
  • Partner slowness stalls the whole answer.

Questions to ask:

  1. "If the partner is slow, do we wait or answer without them?"

    If they say "We wait" → ask "Can we set a time limit and say 'partner unavailable'?"

    Builds credibility: You protect users from what you can't control.

  2. "How do we hear about partner outages?"

    If they say "From users" → ask "Can we watch their error rates and status pages?"

    Builds credibility: You aim to know before users do.

  3. "What does our partner contract say about uptime?"

    If they say "Not sure" → ask "Can vendor management share the terms?"

    Builds credibility: Contracts are reliability levers at your level.

Actions Across Devices

What users see: Ask on one device and have something happen on another, with permission.

How it's probably built: Probably agent orchestration in the cloud, push messaging to devices (Azure Notification Hubs or Web PubSub), permission checks, and protection against doing the same action twice.

Touches: Orchestrator, Tools and agents, Background messaging, App on PC or phone, Sign-in

Where the time goes: Not about the first word: about whether the action happened, once, on the right device.

What breaks:

  • The target device is offline, so the action never happens.
  • An action runs twice after a retry.
  • Permission missing, so it fails silently.

Questions to ask:

  1. "How does the user know the action actually happened?"

    If they say "They'll see it" → ask "Can we confirm it back to them explicitly?"

    Builds credibility: You close the loop on actions, not just requests.

  2. "What stops an action running twice?"

    If they say "Not sure" → ask "Can we test a retry and see?"

    Builds credibility: Duplicate actions are a classic agent risk.

  3. "What happens if the other device is off?"

    If they say "It waits" → ask "For how long, and does the user know?"

    Builds credibility: You think through the unhappy path.

Over-the-Air Updates

What users see: The app and on-device models update themselves.

How it's probably built: Probably delivered through the CDN, with staged rollouts and feature flags in App Configuration so changes reach a few users first.

Touches: CDN and edge, Settings and flags, App on PC or phone

Where the time goes: Not request latency: a bad update hits everyone who installs it.

What breaks:

  • A bad update reaches everyone at once.
  • Devices end up on different versions (version skew).
  • Downloads fail in one region.

Questions to ask:

  1. "Do updates go to a small group first?"

    If they say "Sometimes" → ask "Can staged rollout be the default?"

    Builds credibility: You push for safe change without owning the release.

  2. "How fast can we stop or roll back a bad update?"

    If they say "Pretty fast" → ask "Who can do it, and is it in the runbook?"

    Builds credibility: You turn 'pretty fast' into a plan.

  3. "How many versions are live right now?"

    If they say "A few" → ask "Which is oldest, and do we still support it?"

    Builds credibility: Version skew explains many odd bugs.

Glossary

CDN
Content delivery network: servers near users that serve files fast.
WAF
Web application firewall: blocks bad traffic at the edge.
Origin
The real service behind the CDN.
DNS
The internet's phone book: turns names into addresses.
TLS / certificate
What makes the padlock work; it expires.
API
A way for one program to ask another for something.
Gateway
The single front desk all requests pass through.
Token (auth)
A sign-in pass the app shows to each service.
Token (AI)
A word piece; models read, write, and bill by tokens.
TTFT
Time to first token: how long until the first word appears.
TTLT
Time to last token: how long until the answer finishes.
p95
The time 95% of requests beat; the slow tail users notice.
TPM / RPM
Tokens per minute / requests per minute: model capacity limits.
Context window
How much the model can read at once.
RAG
Retrieval-augmented generation: look up documents, then answer.
RU
Request unit: how Cosmos DB measures and bills work.
Partition
A drawer in the Cosmos DB filing cabinet; one hot drawer slows things.
Replication lag
Delay before data copied to another region shows up there.
TTL
Time to live: an automatic delete-after rule.
Cold start
Slow first request while a server starts up.
Replica
One running copy of a service.
Feature flag
A switch to turn a feature on or off without a release.
