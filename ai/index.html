Supporting an AI Product: What's Different

How AI backends fail, the path an AI request takes, and the 8 numbers a senior manager should know every week.

Use This When

You support the backend of an AI assistant and need to know what's different about keeping it reliable, what to measure every week, and where to start. Everything here is written for a cross-device AI assistant: client apps on devices, cloud services on Azure, and a third-party model provider. Confirm the specifics of your own setup with your team.

How AI Backends Fail

Traditional services mostly fail by being down or slow. AI products fail in five ways, and the last three are easy to miss with traditional monitoring.

The AI Request Path

Every AI request takes roughly this path. Most problems live at one of these hops, and your telemetry needs to see each one.

  1. Client app on the device sends the user's request (possibly after some on-device processing; confirm which requests run where).
  2. Front door / API on Azure receives it, checks identity, and applies rate limits.
  3. Orchestration or agent builds the prompt: system instructions, conversation history, user context.
  4. Retrieval and tools fetch data or take actions (search, calendar, device settings) before or during generation.
  5. Model provider generates the answer and streams it back token by token.
  6. Streaming response flows back to the device. The user sees words appear.

A token is a chunk of text, roughly ¾ of a word. Models read and write in tokens, and providers charge and limit by tokens.

Where to Start

  1. TTFT and TTLT measured and on a dashboard. Users feel these first. See AI Latency.
  2. Throttling and quota alerts at 80%, routed to PagerDuty. This is the most common cause of AI outages. See Tokens, Quotas & Cost.
  3. Prompt and model changes treated like deploys: annotated, canaried, and easy to roll back. See Quality & Safety.
  4. One quality signal with a threshold that makes a drop an incident.
  5. A fallback path for the model provider, pre-approved as a lever.

What Actually Happens

The team measures uptime and error rate, and calls it reliable.
Counter: ask "if the assistant gave wrong answers fast, would anything turn red?" Most AI quality incidents are invisible to traditional monitoring.
"The provider is slow" becomes the explanation for everything.
Counter: ask for the breakdown of a slow request: how much time was retrieval, tools, waiting in a queue, and the model itself? It's often your side.
Prompt changes ship like config, with no review.
Counter: a prompt change is a code change for an AI product. Same canary, same annotation, same rollback.
