Reliability Field Guide

SLOs From Zero

From picking a user journey to a signed SLO and error budget policy in about six weeks, measured from data you already have.

Why It Matters

  • For the business: an SLO turns "is the assistant reliable?" from an opinion into a number, and the error budget turns "reliability or features?" into a rule instead of an argument.
  • For you: SLOs are a central SRE leader's strongest tool for influence. You can't order a pod to fix something, but you can show its SLO burning in front of its manager and your boss, and point to a signed policy that says what happens next.

What the Workbook Says

  • Start from the user's point of view. An SLI is the proportion of good events out of valid events, measured as close to the user as practical. (Workbook, Ch. 2 (opens in a new tab))
  • Start with a few, achievable SLOs, based on current performance, then tighten over time. Aspirational targets nobody can hit get ignored.
  • SLOs need stakeholder agreement: product, the engineering owner, and SRE. Otherwise there are no consequences when they're missed.
  • Write it down: an SLO document and an error budget policy, reviewed regularly. (Appendix A: Example SLO Document (opens in a new tab) · Appendix B: Example Error Budget Policy (opens in a new tab))
  • Learn from others' attempts: the case studies show that starting simple and iterating beats waiting for perfect measurement. (Ch. 3: SLO Engineering Case Studies (opens in a new tab))

Reality Check

  • SRE doesn't own the code. You can measure SLIs from existing request data in Application Insights without the pods changing anything. Start there.
  • Azure Managed Grafana has no built-in SLO feature. You build an SLO dashboard yourself: a KQL query, a target line, and a budget panel.
  • The product is AI. "Success" must include speed (TTFT) and arguably quality, not just HTTP 200. Start with success plus TTFT; add quality later.
  • Firefighting leaves little time. Do one journey end to end first, rather than five halfway.

Before You Start

  • The observability foundation is good enough: request data for the journey is in Application Insights.
  • One SRE engineer has about 20% of their time for 6 weeks.
  • A product partner and the owning pod's manager have agreed to take part.
  • Your boss has agreed to sign the error budget policy.

How to Sell It

To your boss
Right now "is the assistant reliable?" is answered by gut feel, and reliability vs feature work is argued case by case.
I want to pilot one SLO on [journey] over 6 weeks: measured from data we already have, agreed with [pod] and product,
with an error budget policy you sign. Then we report one clear number monthly, and when the budget is gone,
there's a pre-agreed response instead of a fight. Ask: your signature on the policy, and a note to [pod manager] backing it.
To a pod manager
We'd like to agree one SLO with you for [journey]. SRE does the measuring and the dashboard; we'd need about 2 hours of
[engineer]'s time to confirm what "good" means. The benefit for you: a clear line for when reliability work
outranks features, decided in advance, instead of SRE escalating every bad week. And when the budget is healthy,
you get evidence that you can ship faster.

Copy-Ready Artifacts

One-page SLO document
SLO: [journey name]         Owner (pod): [team]    SRE contact: [name]    Product: [name]
Status: [draft / agreed]    Agreed on: [date]      Review: quarterly

User journey:  [what the user is trying to do]
SLI:           % of [valid requests] that [succeed] AND [TTFT < N s]   (source: Application Insights, query: [link])
Target:        [99.5%] over a rolling [28 days]
Error budget:  [0.5%] of requests = about [X] bad requests per window
Dashboard:     [Grafana link]
Alerts:        burn-rate page via PagerDuty service [name]; slow-burn ticket
Exclusions:    [e.g. requests from internal test accounts]
Rationale:     [why this target: current performance, user expectations]
Error budget policy (starting point)
Error Budget Policy: [service]     Signed: [boss], [pod manager], [SRE manager]   Date: [date]

While budget remains: normal release pace.
When 50% of the budget is spent in a window: review the top contributors in the weekly SRE/pod sync.
When 100% is spent: non-critical launches pause until the SLI is back within target for [7] days,
  and the pod's top reliability action becomes its #1 priority.
Exceptions: [boss] may grant an exception in writing.
Single incident using more than 20% of the budget: requires an RCA.

How You'll Know It's Working

  • Leading: the SLO dashboard is opened in every SRE Daily. The target is signed. Burn-rate alerts exist.
  • Lagging: SLO attainment trends up over a quarter. At least one decision (a launch held, or work prioritized) cited the budget. Fewer "is it reliable?" debates in leadership meetings.

What Actually Happens

Everyone wants 99.99% on day one.
Counter: show the baseline. If you're at 98.7% today, 99.99% is fiction. Start at 99% or 99.5% and earn the next nine.
The SLO gets agreed, then ignored.
Counter: the signed error budget policy and the monthly leadership report are what give it teeth.
Arguments about the perfect SLI delay everything.
Counter: ship a good-enough SLI in week 2, and improve it in version 2.
