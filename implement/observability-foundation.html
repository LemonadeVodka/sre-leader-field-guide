Reliability Field Guide

Observability Foundation

Make the critical path of your top user journeys visible end to end, including the model call, with one official dashboard per service.

Why It Matters

  • For the business: you can't fix what you can't see. Unclear telemetry is why incidents stall on "we don't know where it's failing."
  • For you: every other program depends on this. SLOs need SLIs, alerts need signals, RCAs need evidence, and surfacing well needs dashboards SRE can actually open.

What the Workbook Says

  • Monitoring should answer two questions: what's broken, and why. Symptoms (user impact) drive alerts; causes help diagnosis. (Workbook, Ch. 4: Monitoring (opens in a new tab))
  • Use the right source for the job: metrics for trends and alerting, and logs (and traces) for detailed investigation.
  • Treat monitoring configuration like code: versioned and reviewed, so dashboards and alerts don't silently drift.
  • Prefer a small set of trusted dashboards over many unowned ones. (SRE Book, Ch. 6 (opens in a new tab))

Reality Check

  • Instrumentation lives in pod code. SRE can define the standard and check coverage, but pods add the spans and attributes. Keep the asks small and specific.
  • Coverage is probably uneven. Some services are well instrumented, some barely. Start with the user's critical path.
  • Client-side visibility may be mostly in Pendo, not OTel. Decide what you need from the device side.
  • Telemetry costs money. Agree on sampling and retention, so coverage doesn't become a finance problem.

Before You Start

  • You've done Observability Day One, and know your actual setup.
  • The critical user journeys are named (shared with the SLO program).
  • One SRE engineer to own the standard and the coverage tracking.

How to Sell It

To your boss
In [N] of last quarter's incidents, we lost time because we couldn't see where requests were failing.
I want to make the critical path of our top journeys fully visible end to end, including the model call (TTFT, tokens),
with one official dashboard per critical service. It's mostly small, specific asks to pods, plus SRE time.
It's the foundation for SLOs, better alerts, and faster incidents. Ask: help us get it into pod planning.
To a pod manager
One small ask: can your team add [attribute/span, e.g. TTFT and token counts on the model call] using our telemetry standard?
It's roughly [estimate] of work. In return, when something breaks we can point to the exact hop with evidence,
instead of paging you to go look.

Copy-Ready Artifacts

Telemetry standard (one page)
Applies to: every production service on the critical path.
1. OpenTelemetry instrumentation exporting to Azure Monitor / Application Insights.
2. service.name: [pod]-[service], the same in every environment; deployment environment set as an attribute.
3. Trace context propagated across every hop (and from client apps where possible).
4. Model calls: one span each, with model name, input/output token counts, TTFT (first chunk) and total duration.
5. Tool calls: one span each, with tool name and success/failure.
6. Logs include the trace ID; no personal data in attributes or logs.
7. Sampling: 100% of errors; [x%] of successful requests. Retention: [n] days.
8. One official Grafana dashboard per service, golden signals on top, owner named.

How You'll Know It's Working

  • Leading: % of the critical path covered; % of services following the standard; official dashboards in place.
  • Lagging: fewer "couldn't see it" gaps in RCAs; faster time to identify the failing hop; SLIs measurable for every top journey.

What Actually Happens

"Improve observability" never gets prioritized.
Counter: break it into one small, named ask per pod, each tied to a specific incident it would have helped.
Dashboard sprawl continues.
Counter: "official" dashboards are marked as such and linked from runbooks. Others are fine, but they aren't what incidents use.
The telemetry bill spikes.
Counter: the sampling and retention policy, plus a monthly cost check with a named owner.
